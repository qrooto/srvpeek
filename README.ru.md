# srvpeek

[English](README.md) | [Русский](README.ru.md)

Один бинарник для знакомства с незнакомым Linux-сервером. Показывает ресурсы, сетевую конфигурацию, сокеты и их владельцев, systemd, расписания и Docker. Читает состояние системы, не меняет её настройки и не требует установленного Go или дополнительных библиотек для запуска готового бинарника.

Главный принцип: **неизвестное не считается отсутствующим, а успешный сбор не означает исправность системы**. Интерфейс, справка и диагностические сообщения — на английском. Имена, пути и содержимое источников сохраняются на языке системы.

## Установка для запуска командой `srvpeek`

После сборки `make build` установите бинарник в каталог из `PATH`:

```bash
sudo install -m 0755 dist/srvpeek /usr/local/bin/srvpeek
command -v srvpeek
srvpeek
```

Для другого сервера выбирайте сборку по архитектуре **сервера**, которую можно узнать через `uname -m`: `x86_64` → amd64, `aarch64` → arm64.

На машине с проектом:

```bash
# Для aarch64 используйте dist/srvpeek-linux-arm64.
scp dist/srvpeek-linux-amd64 user@server:/tmp/srvpeek
```

На сервере:

```bash
sudo install -m 0755 /tmp/srvpeek /usr/local/bin/srvpeek
srvpeek
sudo srvpeek # по необходимости: больше сведений с учётом ограничений системы
```

Каталог `/usr/local/bin` должен входить в `PATH`. Без административных прав можно установить бинарник в `~/.local/bin`, убедившись, что этот каталог входит в `PATH` вашей оболочки. Сам по себе запуск `srvpeek` не повышает привилегии: ограничения доступа будут явно указаны в отчёте.

## Использование

`dist/srvpeek` — сборка для машины разработки. Для запуска из проекта:

```bash
./dist/srvpeek
sudo ./dist/srvpeek
./dist/srvpeek ports
./dist/srvpeek containers
./dist/srvpeek --full
./dist/srvpeek --color always
./dist/srvpeek --color never
./dist/srvpeek --timeout 8s
./dist/srvpeek --json
./dist/srvpeek --save snapshot.json
```

Флаги ставятся перед именем раздела. Разделы: `system`, `disks`, `network`, `ports`, `services`, `timers`, `cron`, `containers`, `firewall`. Имя раздела включает полный вывод для него.

Сборщики работают параллельно. Таймаут по умолчанию — 4 секунды на раздел, включая все последовательные команды этого раздела. Ограничение для stdout и stderr каждой команды — по 2 MiB, для каждого файла — 2 MiB. При превышении лимита соответствующий ответ отбрасывается. Зависшие чтения файлов не задерживают выдачу отчёта за пределами таймаута раздела; команды по таймауту останавливаются вместе с их группами процессов.

`--save` создаёт новый JSON-файл с правами 0600 и отказывается перезаписывать существующий.

## Вид отчёта и цвета

В начале — обзор статусов сбора по всем разделам. Далее идут блоки с разделителями, таблицами, переносом длинных значений и отдельными сообщениями об ошибках. Ширина таблиц подстраивается под терминал; на узких экранах используются записи с подписями полей.

Публикации портов Docker отображаются как `host:port → container-port/protocol`. Для полного структурированного снимка используйте `--json`.

По умолчанию действует `--color auto`: цвет включается только для терминала, если `TERM` не равен `dumb` и переменная `NO_COLOR` не установлена. `--color always` принудительно включает цвет, `--color never` отключает. При перенаправлении в файл цвет по умолчанию отключён. В JSON и сохранённые снимки управляющие последовательности оформления не добавляются.

Цвет относится к сообщённым состояниям и проблемам сбора, а не к общей оценке здоровья сервера. Все статусы подписаны и читаются без цвета.

## Значение статусов

`ok` (`COLLECTED` в текстовом отчёте) — сведения получены в заявленной области проверки. Это не подтверждение исправности приложений.

`partial` — часть сведений получена, но сбор неполон или источник сообщил предупреждение. Остальные статусы: `timeout`, `missing_tool`, `denied`, `unavailable`, `error`, `parse_error`, `truncated`, `warning`.

Проблемы привязаны к конкретному источнику и сохраняются в JSON. При ошибке команды её stdout не используется. Даже при коде выхода 0 любой stderr приводит к `warning` и отказу от интерпретации stdout: некоторые инструменты сообщают об отказе доступа только через stderr. Неожиданный формат не превращается в пустой список.

В JSON указаны версия схемы, время начала и длительность отчёта и разделов, область проверки, данные, примечания и проблемы. Поле `data` отсутствует, если полезные сведения не получены. Успешный ответ `[]` — явный пустой список проверенного источника. Снимок не атомарен: процессы и контейнеры могут измениться между запросами.

Коды выхода:

- `0` — все выбранные разделы собраны без зафиксированных проблем; это не код здоровья сервера.
- `1` — есть неполные или недоступные разделы; отчёт всё равно выдан.
- `2` — неверные аргументы или ошибка записи отчёта.

## Область проверки и ограничения

| Раздел | Что собирается | Ограничения интерпретации |
|---|---|---|
| system | ОС, ядро, uptime, load, видимые процессу CPU, RAM/swap из procfs | Load не является CPU%. Procfs может отражать хост, а не лимиты cgroup |
| disks | Выбранные типы локальных FS, блоки, доступное обычному пользователю место, inode, read-only | Не аудит всех FS; bind/overlay нельзя суммировать. Сетевые и псевдо-FS исключены |
| network | Интерфейсы и маршруты IPv4/IPv6 через `ip -j`, resolv.conf | Нет проверок связности, DNS и интернета; split-DNS может быть не виден |
| ports | TCP LISTEN, UDP UNCONN через `ss`, сообщённые владельцы, executable и кандидаты .service из cgroup | Не внешняя доступность; публикации через NAT могут отсутствовать. Неизвестный владелец не означает отсутствие процесса. При сопоставлении PID возможны гонки |
| services | Загруженные системные service units и установленные unit files | active не проверяет приложение; inactive и disabled не диагноз. User managers не проверяются |
| timers | Таблица системных systemd timers без угадывания формата дат | Не результат последнего запуска; пользовательские таймеры исключены |
| cron | `/etc/crontab`, `/etc/cron.d`, два стандартных spool-пути, periodic directories, anacrontab | Наличие файла не подтверждает исполнение; строки могут быть переменными или неверными заданиями. Нестандартные spool и at не проверяются |
| containers | Контекст Docker CLI, все контейнеры, state/health, сети/IP, порты, mounts, restart policy, Compose project/service | Контекст может указывать на другую машину. running не означает healthy. Отсутствующий Health — отсутствие сообщённой проверки. Podman/CRI исключены |
| firewall | JSON ruleset nftables | Нет расчёта эффективных разрешений. Legacy iptables, eBPF, внешние firewall и cloud ACL исключены |

Системные команды используются при наличии: `ip`, `ss`, `systemctl`, `docker`, `nft`. Если команды нет, утилита явно это сообщает. Docker не обязателен для запуска самой утилиты. Docker CLI использует текущий контекст и окружение; отчёт показывает имя контекста и наличие переменных переопределения, не раскрывая их значения.

Управляющие символы терминала удаляются из отображаемых данных. Docker Env, аргументы команд контейнеров и healthcheck logs не запрашиваются. Снимки всё равно могут содержать чувствительные адреса, пути, mounts, имена и содержимое cron-файлов. Утилита сама не отправляет отчёты; Docker CLI может обращаться к daemon согласно выбранному контексту.

## Сборка и тестирование

Нужен Go 1.23 или новее. Внешних Go-зависимостей нет.

```bash
go test ./...
go vet ./...
make build
make release # статические Linux-бинарники amd64 и arm64
```

Либо напрямую:

```bash
CGO_ENABLED=0 go build -buildvcs=false -trimpath -ldflags='-s -w' -o srvpeek .
```

Текущая версия не выполняет HTTP/TCP probes, не анализирует журналы, не поддерживает Podman и не сравнивает снимки. Сохранённый JSON можно использовать для анализа и будущего сравнения.
